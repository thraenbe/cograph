# F27 benchmark: Shelf in-frame call lines (2026-10-07)

**Read this first.** On main, Shelf paints **zero** in-frame call lines, in every view and in every repo measured. Every
comparison below is therefore between a Shelf that drew no in-frame call lines at all and one that finally does. The
question is not whether F27 costs something. It does. The question is whether drawing the call structure inside a folder
is worth that cost.

All numbers predate session-215's `this.method()` analyzer fix (analyze_ts.js / analyze_js.js). That fix does **not**
touch django, flask (Python) or fmt (C++). Its effect on a JS/TS repo is measured separately on nest (section 6).

### 1a. Correction: one contaminated sample, now excluded

The first draft argued that the django Static working-zoom cell was noise, citing a 57.5 fps run that "did the least
main-thread work of all nine". **That run was not a working-view measurement.**
- The cause was a bench bug: a view whose "enter view" step was skipped still had its gestures measured, at the previous
  zoom, under the view's name.
- An audit of all bench runs found exactly one affected phase-1 run: django Static, F27, rep 3, fit-relod and working.
  It is excluded above. Every other phase-1 run entered all three views.
- The bug is fixed in bf2f64c: views are aimed from state frame geometry, and a view that cannot be entered fails the run.

## 2. Method

- **Builds**, each in its own detached worktree cut from main. Nothing points at another session's worktree.
  - main = `1fc1156`.
  - F27 = `c30cb0e`: main plus only c2c548d's `rendering.js` hunk.
  - F27+U1 = `9f66ea3`: the F27 build plus U1's 18e36b7 and f1adf7f, with the setting on (its default).
  - `frameRender.js` is byte-identical to main in all three.
- **Harness**: uxtest `bench` project (`uxtest/bench/shelf-lines.spec.ts`).
  - One Playwright worker, headed Chromium (GPU raster), `--disable-gpu-vsync --disable-frame-rate-limit`. fps above the
    display refresh is real headroom.
  - Real pointer gestures: a 90-step mouse drag for pan, 24 wheel ticks for zoom. Programmatic zoom transforms would
    bypass the gesture path.
  - Shelf only, Static and Dynamic.
- **Per run**:
  - Settle after Detail 1.
  - Then three views. **fit**: as users reach it right after Detail 1. **fit-relod**: zoomed in past the link LOD and
    fitted again. **working**: k ~0.85-0.9 on the largest frame.
  - Per gesture: fps, p95 frame time, long frames, and main-thread CPU per frame (`Performance.getMetrics`).
  - A mid-gesture probe: painted in-frame lines, plus the culler's own `__cull.want.links` and the in-view link count it
    decided on.
- **Runs**: 3 repetitions, builds interleaved with a rotating order, release-matrix repos django, fmt, flask. 54 runs,
  0 failures. 1-minute load average at test start: median 3.85, most of it the benchmark's own browser.

## 4. Which case each repo hit (F27 build)

| repo | fit (as reached) | fit-relod | working (k ~0.85-0.9) |
|---|---|---|---|
| django | parked by zoom (0 lines in the DOM; this repo is **not** stuck at fit) | parked by zoom | **painted throughout** (394 in view) |
| fmt | **STUCK (F29)**: `want.links=false`, 5819 painted | parked by zoom | **painted throughout** (2801 in view) |
| flask | **STUCK (F29)**: 299 painted; harmless at that count (70 vs 71 fps) | parked by zoom | **painted throughout** (257) |

**"Parked by gesture" was never observed.** The gesture budget (`gestureBudget`) parks in-frame links during a pan or zoom
only when more than 5000 are in view. The only measured view above 5000 is fmt's stuck fit. There the gesture budget
cannot act either: it goes through the same `applyLod`, and with `want.links` already false, `wantChanged` stays false.

So the belief that "the LOD parks them while panning" is true at fit on big repos for the wrong reason (the zoom LOD), and
false exactly where F27's cost lands. In the working view the gesture budget keeps the lines painted, under budget. That
is the case that generalises: any folder with fewer than 5000 in-view in-frame lines at a zoom >= 0.4 pays F27's per-frame
cost while panning.

## 9. Harness findings

- **A measurement harness that silently mislabels where it measured is worse than one that crashes.** Until bf2f64c,
  the bench behaved like this:
  - a view whose "enter view" step was SKIPPED (no frame title found to aim at) still had its pan and zoom measured, at
    whatever zoom it happened to be at;
  - the result was recorded under that view's name, and the run PASSED.

  Every number it produced looked fine. It contaminated one phase-1 run (django Static F27 rep 3), and it was the sample
  the first draft's "noise" argument rested on. It also voided the first nest matrix. The fix:
  - the aim comes from state frame geometry (`state.frames`, `f.abs`) instead of DOM titles;
  - **a view that cannot be entered fails the run.**

  The second half is the part that matters.
- **A first nest matrix was voided.** nest fits at k 0.051, and the bench's zoom step stopped at k 0.379, below the
